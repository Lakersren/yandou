# Ant Design Pro 运营后台设计

日期：2026-09-14

## 目标

为海淘补货机器人建设一套标准、规范的企业后台。后台由一名运营人员日常使用，核心操作是粘贴商品 URL 并开始监控。系统自动处理商城识别、检查频率、库存基线、站点归属和通知范围，不要求运营人员配置解析规则。

## 设计原则

- 使用 Ant Design Pro 的标准后台信息架构和交互规范。
- 日常操作界面与技术维护界面分离。
- 添加商品只有商品 URL 一个必填字段。
- 用规范的表格、筛选、弹窗、状态标签和反馈组件表达业务状态。
- 不在运营界面暴露解析器、CSS 选择器、任务队列、Webhook 密文和原始响应。
- 保留现有 Django 监控、库存状态机、Celery 调度和钉钉通知能力。

## 信息架构

运营后台位于 `/console/`，包含以下模块：

1. 工作台
   - 监控商品数
   - 当前现货规格数
   - 最近 24 小时补货数
   - 最近 24 小时异常数
   - 最近监控商品
   - 最近补货和异常摘要
2. 商品监控
   - 商品列表
   - 名称或 URL 搜索
   - 商城和库存状态筛选
   - 添加、暂停、启用、立即检查和移除
   - 商品详情抽屉
3. 补货记录
   - 商品、规格、价格、补货时间
   - 站点群与综合群发送结果
4. 异常记录
   - 抓取、解析和通知异常
   - 最近发生时间、连续失败次数和重新检查
5. 钉钉群
   - 站点群和综合群配置
   - Webhook、加签密钥、启用状态和测试发送

顶部栏显示菜单折叠、服务状态和当前用户。侧栏使用 Ant Design Pro 深色导航。Django Admin 保留在 `/admin/`，仅供技术维护，不作为运营入口。

## 视觉规范

- 页面背景：`#f0f2f5`
- 主色：Ant Design Blue `#1677ff`
- 侧栏：`#001529`
- 内容容器：白色
- 主文字：`rgba(0, 0, 0, 0.88)`
- 次要文字：`rgba(0, 0, 0, 0.45)`
- 边框：`#f0f0f0`
- 成功：`#52c41a`
- 警告：`#faad14`
- 错误：`#ff4d4f`
- 默认圆角遵循 Ant Design token，不自定义夸张圆角或渐变。
- 表格和筛选区保持企业后台的信息密度，桌面为主要使用场景，同时保证手机端不溢出。

## 核心交互

### 添加商品

1. 运营点击“添加监控商品”。
2. 系统打开标准弹窗，仅显示商品 URL 输入框。
3. 运营粘贴 URL 并点击“开始监控”。
4. 按钮进入加载状态，禁止重复提交。
5. Django 根据域名匹配已支持商城，抓取商品并判断库存。
6. 成功时建立首次库存基线，关闭弹窗，将商品插入列表顶部并显示成功消息。
7. 无法识别时保留弹窗并显示简短错误，不创建无效商品。
8. URL 已存在时关闭弹窗并打开已有商品详情。
9. URL 对应商品已被软删除时，恢复原商品、重新建立库存基线并保留历史记录。

默认行为：

- 使用商城默认检查间隔。
- 通知所属站点群。
- 通知综合群。
- 首次检查只建立库存基线，不发送补货通知。
- 有货连续确认两次后才产生补货事件。

### 商品管理

商品列表展示名称、URL 摘要、商城、规格和价格、库存、最近检查时间与操作。点击名称或“详情”打开右侧抽屉，不离开列表。

行级操作包括：

- 立即检查：提交异步任务并显示已提交状态。
- 暂停或启用：即时更新列表状态。
- 移除：二次确认后软删除，保留历史快照、补货记录和通知记录。

### 异常处理

异常列表区分抓取失败、库存无法识别和钉钉发送失败。运营只看到商城、商品、可读原因、时间和“重新检查”操作。技术堆栈和原始响应仅在 Django Admin 中可见。

## 系统架构

前端使用 React、TypeScript、Vite、Ant Design 和 Ant Design Pro Components，构建后由 Nginx 提供静态资源。后端继续使用 Django，新增同域 JSON 接口。前后端使用现有 Django Session 登录和 CSRF 保护，不引入新的令牌体系。

```text
Browser /console/
        |
        | same-origin JSON + Django session + CSRF
        v
Django API
  |-- PostgreSQL
  |-- Redis / Celery
  |-- 商城适配器
  `-- 钉钉通知
```

前端不直接访问商城、Redis、数据库或钉钉。所有外部访问和状态判断都在 Django 服务中完成。

## 前端组件边界

- `ConsoleLayout`：侧栏、顶部栏、面包屑和路由出口。
- `DashboardPage`：统计、最近商品、补货与异常摘要。
- `ProductsPage`：筛选、分页、数据表格和行操作。
- `AddProductModal`：URL 校验、提交、加载和错误状态。
- `ProductDrawer`：商品、规格、库存和最近检查信息。
- `RestockEventsPage`：补货记录和通知结果。
- `FailuresPage`：异常记录和重新检查。
- `DingTalkChannelsPage`：群配置和测试发送。
- `apiClient`：同域请求、CSRF、错误标准化和登录失效处理。

每个页面只依赖统一 API 类型，不读取 Django 模型内部字段。

## API 设计

所有接口位于 `/api/console/v1/`，只接受已登录员工账号。

- `GET /session`：当前用户和服务状态。
- `GET /dashboard`：工作台统计与摘要。
- `GET /products`：商品筛选和分页。
- `POST /products`：提交一个 URL 并建立监控。
- `GET /products/{id}`：商品和规格详情。
- `PATCH /products/{id}`：启用或暂停。
- `DELETE /products/{id}`：软删除。
- `POST /products/{id}/check`：立即检查。
- `GET /events`：补货记录分页。
- `GET /failures`：异常记录分页。
- `POST /failures/{id}/retry`：重新检查对应商品。
- `GET /dingtalk-channels`：钉钉群列表，密钥只返回掩码和是否已配置。
- `POST /dingtalk-channels`：新增钉钉群。
- `PATCH /dingtalk-channels/{id}`：修改钉钉群；空密钥表示保留原值。
- `POST /dingtalk-channels/{id}/test`：测试发送。

统一成功响应包含 `data`；统一错误响应包含 `code`、`message` 和可选字段错误。接口不返回 Python 异常、完整 Webhook 或密钥。

## 数据变更

现有模型继续使用，增加以下字段：

- `Product.deleted_at`：软删除时间；默认查询排除已删除商品。
- `Product.created_by`：记录添加商品的后台用户，可为空以兼容已有数据。

现有库存快照、补货事件和通知记录关联关系不变。软删除商品不再参与调度，但历史记录仍可查询。

Celery Beat 每分钟更新 Redis 中的调度心跳。`GET /session` 仅在心跳时间不超过 180 秒时返回“服务正常”，超过阈值时返回“调度异常”。控制台不得使用写死的运行状态。

## 错误和状态

### 添加 URL

- URL 格式错误：输入框字段错误。
- 商城不支持：提示“暂不支持这个商城”。
- 页面无法访问：提示“商城页面暂时无法访问，请稍后重试”。
- 库存无法识别：提示“暂时无法识别该商品库存”。
- 重复 URL：打开已有商品详情，不重复创建。
- 已软删除 URL：恢复原商品并重新建立库存基线。

### 后台任务

- 抓取错误不覆盖最后一次确认库存。
- 有货必须连续确认两次。
- 钉钉发送失败自动重试三次。
- 同一补货事件和群组合只允许一条成功通知。
- 连续失败在异常模块显示，不向普通商品状态伪装成缺货。
- 异常接口合并抓取异常与发送失败通知，使用统一的前端异常类型区分。

### 前端状态

每个数据页具备加载、空数据、错误和正常四种状态。提交操作使用局部加载状态，不阻塞整个页面。登录失效时跳转 Django 登录页并保留返回地址。

## 安全

- 沿用 Django Session、员工权限和 CSRF 防护。
- Console API 强制 `is_staff`。
- 商品 URL 只能属于已配置商城域名，并保留公网地址检查和跳转域名检查。
- 钉钉 Webhook 与密钥继续加密落库。
- API 永不返回完整 Webhook、加签密钥或原始页面内容。
- 删除采用软删除并要求确认。
- Nginx 只公开 `/console/`、必要 API、登录页和静态资源；Django Admin 可通过安全组或额外访问控制限制。

## 部署

Docker Compose 保留 PostgreSQL、Redis、Django Web、Celery Worker、Celery Beat 和 Nginx。增加 Node 构建阶段，将前端静态产物复制到 Nginx 镜像或 Django 静态目录。生产环境只运行构建产物，不运行 Vite 开发服务器。

部署顺序：

1. 构建前端和后端镜像。
2. 执行数据库迁移。
3. 启动 Django、Worker 和 Beat。
4. 启动 Nginx。
5. 检查 `/healthz`、`/console/` 和任务队列。

## 验收标准

- 登录后默认进入 `/console/`，页面符合确认的 Ant Design Pro 布局。
- 运营添加商品时只填写 URL。
- 支持的 URL 能自动建立监控，失败时不产生无效商品。
- 商品列表能筛选、分页、暂停、立即检查和软删除。
- 补货、异常和钉钉群均有独立标准页面。
- 日常控制台不出现解析器、选择器、Redis、Celery、密钥原文或原始响应。
- 原有库存判断和钉钉通知行为不回归。
- 自动测试、桌面与手机视觉检查、Docker 健康检查全部通过。

## 非目标

- 不提供公众注册。
- 不建设多租户或套餐计费。
- 不增加个人订阅偏好。
- 不支持运营人员自行编写商城解析规则。
- 不重写现有爬虫、库存状态机或钉钉通知核心。
